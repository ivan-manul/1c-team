# Правила кода 1С

## Где писать
- Если в проекте код пишется в задачу, а не в модули (см. CLAUDE.md), — пиши его в `код.md` папки задачи по шагам плана, модули не трогай.
- Метаданные меняй через unica (`unica:meta-add`, `unica:meta-edit`, `unica:form-edit`), код — через `unica:code-patch` или правкой модулей.
- Делай только то, что есть в согласованном плане. Проблемы вне задачи — упомяни, не чини.

## Код
- Стиль окружающего кода, русские имена.
- Функция — существительное по возвращаемому значению (`СуммаДокумента`, не `ПолучитьСумму`/`РассчитатьСумму`); процедура — глагол (`ЗаполнитьТабличнуюЧасть`). Исключение — перехватчики с именем типового метода.
- Строго по стандартам разработки 1С: `unica.docs` (`source: "development-standard"`), если недоступен — скилл `1c-team:standards`.
- Комментариев внутри тела методов и текстов запросов нет.
- Описание перед методом — по стандарту 1С «Описание процедур и функций»: что делает (у функции — «Возвращает …»), «Параметры:», «Возвращаемое значение:»; при необходимости — условие вызова («Вызывается в транзакции»). Без ссылок на ТЗ, требования, историю и подробности реализации.

## Расширение
- Заимствованный метод — всегда `&ИзменениеИКонтроль`.

## Запросы
- Виртуальные таблицы регистров — с отборами в параметрах, а не в ГДЕ.
- Никаких запросов в цикле: пакет, временные таблицы, индексы по полям соединения.
- Разыменование через точку — только где необходимо.
- RLS учтён; `РАЗРЕШЕННЫЕ` — по необходимости.
- Подробнее — `unica:query-optimize`.

## Проверка
`unica.search` вызывай с областью (объект или модуль): без неё на большой конфигурации поиск падает.
После каждого шага — `unica.check` и диагностики (`unica:code-diagnostics`).
