# Спецификация доработки 1С

Папка задачи: `docs/specs/ГГГГ-ММ-ДД-<кратко>/` в корне проекта. Каждый пишет свой файл:
- `тз.md` — спецификация (аналитик), по шаблону ниже;
- `код.md` — план реализации и код, если в проекте код пишется в задачу, а не сразу в модули (разработчик).

Файлы ссылаются друг на друга, а не копируют содержимое. Читай только тот файл, который нужен для твоей работы.

## Правила
- Пиши для разработчика, который не видел переписку: всё нужное — в документе.
- Каждое требование проверяемо. «Удобно», «быстро», «корректно» без числа или примера — не требование.
- Неизвестное не додумывай: вынеси в «Открытые вопросы».
- Ссылайся на реальные объекты конфигурации (имена метаданных), найденные через unica, а не на догадки.
- Не описывай реализацию построчно — это работа разработчика.

## Шаблон

```markdown
# <Название задачи>

Статус: черновик | на согласовании | согласовано
Дата: ГГГГ-ММ-ДД

## 1. Цель
Зачем это нужно бизнесу. 1–3 предложения.

## 2. Текущее поведение
Как сейчас (объекты, формы, отчёты, с именами метаданных).

## 3. Требуемое поведение
Нумерованные требования: Т1, Т2, …

## 4. Сценарии
По одному на ключевой путь: предусловие → действия пользователя → ожидаемый результат.
Включи граничные и ошибочные случаи.

## 5. Данные
Какие объекты/реквизиты/регистры читаются и меняются. Новые объекты — с типами.

## 6. Права и роли
Кто может выполнять действие. Что видит пользователь без прав.

## 7. Нефункциональные требования
Объёмы данных, время отклика, совместимость (платформа, БСП, расширение/конфигурация), обмены.

## 8. Вне рамок
Что явно не делаем.

## 9. Критерии приёмки
Чек-лист, по которому ревьюер и пользователь примут задачу. Связать с Т1…Tn.

## 10. Открытые вопросы
Вопрос → кому → влияние на решение.
```
